Como o PrintHub 3D foi feito

Um guia para estudar o projeto do começo ao fim e apresentar na banca com confiança. Tudo aqui foi tirado do código de verdade do repositório.

① Em uma frase② Explicação simples + analogia③ ▸ Aprofundar: o código linha a linha

Como estudar com este guia

  1. Primeira leitura: leia só as caixas coloridas ("Em uma frase", analogias e "Para falar na banca"). Em 1 hora você entende o projeto todo.
  2. Segunda leitura: abra os botões ▸ Aprofundar e acompanhe o código. Deixe o arquivo aberto no VS Code ao lado.
  3. Treino: leia as perguntas da banca em voz alta e tente responder antes de abrir a resposta.
  4. Ao terminar cada assunto, marque "Já estudei" no fim da seção. A barra no menu mostra quanto falta (fica salvo neste navegador).

Dica: este arquivo funciona sem internet. Para imprimir ou salvar em PDF, use Ctrl+P (todas as partes "Aprofundar" saem abertas).

Assunto 1

O problema e a ideia

Em uma fraseO PrintHub 3D liga quem precisa de uma peça impressa em 3D a quem tem impressora 3D, do pedido até a entrega.

O problema: muita gente precisa de uma peça (um suporte quebrado, uma maquete, um protótipo), mas não tem impressora 3D nem sabe quem faz. Do outro lado, quem tem impressora não tem um lugar organizado para receber pedidos, mandar preço e conversar com o cliente.

A solução: uma plataforma (site + app Android) onde o cliente descreve a peça, os fabricantes mandam orçamentos, o cliente escolhe um, e os dois conversam pelo chat até a peça ser entregue.

É como um "iFood de peças 3D": o cliente faz o pedido, as "cozinhas" (fabricantes) dizem quanto custa e quanto demora, o cliente escolhe uma, e acompanha o preparo até chegar.

Os três papéis

🙋 Cliente

Qualquer pessoa que entra com uma conta Google.

  • Cria pedidos com fotos e arquivos 3D
  • Compara e aceita orçamentos
  • Conversa pelo chat
  • Toca em "Recebi o pedido"
  • Exclui pedido se ninguém está trabalhando nele

Tela: painel-cliente.html (cor azul)

🛠️ Fabricante

Só entra quem foi convidado pelo dono.

  • Vê pedidos abertos
  • Envia orçamento (preço + prazo)
  • Se for escolhido: inicia produção e marca "pronto"
  • Conversa pelo chat

Tela: painel-fabricante.html, chamada de "Oficina" (cor roxa)

👑 Dono da plataforma

Um fabricante especial: o e-mail que está em DONO_EMAIL.

  • Tudo que o fabricante faz
  • Aba Equipe: convida e remove fabricantes
  • Aba Todos: vê todos os pedidos e pode excluir qualquer um

Só pode existir um dono (o banco garante isso).

"O PrintHub 3D resolve a falta de um ponto de encontro entre quem precisa de peças impressas em 3D e quem fabrica. Tem três papéis: cliente, fabricante e o dono, que administra a equipe de fabricantes."
Assunto 2

O caminho do pedido

Em uma fraseTodo pedido passa por 6 etapas, sempre na mesma ordem, e cada etapa tem um "dono" do botão.
abertoCliente criou. Esperando orçamentos.Cliente cria
com_orcamentoChegou pelo menos 1 orçamento.Fabricante orça
aceitoCliente escolheu um orçamento.Cliente aceita
em_producaoA impressora está trabalhando.Fabricante inicia
prontoPeça feita, esperando entrega.Fabricante marca
entregueCliente confirmou que recebeu.Cliente confirma

Azul = quem aperta é o cliente. Roxo = quem aperta é o fabricante. Os nomes em código são exatamente os valores gravados na coluna status do banco.

Repare em duas decisões importantes:

  • Quem marca "entregue" é o cliente, não o fabricante. Assim o fabricante não consegue dizer que entregou sem o cliente confirmar. Por isso existe a etapa pronto no meio (ela foi criada depois, na migração 03).
  • Não dá para pular nem voltar etapas. O servidor tem uma "tabela de próximo passo" e só aceita andar uma casa.
É como rastrear uma encomenda nos Correios: "postado → em trânsito → saiu para entrega → entregue". Ninguém pula de "postado" direto para "entregue".
Aprofundar: como o servidor impede pular etapas src/rotas/pedidos.js
  1. 1Um "dicionário": para cada status atual, qual é o próximo. Só existem duas entradas, então o fabricante só consegue fazer aceito → em_producao e em_producao → pronto.
  2. 2PATCH /api/pedidos/:id/status. Antes de entrar na função, exigirTipo("fabricante") barra quem não é fabricante.
  3. 4Busca o pedido no banco usando a regra de permissões (assunto 5).
  4. 6–8Mesmo sendo fabricante, tem que ser o escolhido desse pedido. Se não for: erro 403 (proibido).
  5. 9–10Procura o próximo status. Se o atual for pronto ou entregue, não existe próximo: erro 400.
  6. 12–13Grava o novo status no banco e devolve o pedido atualizado.
  7. 16Qualquer erro inesperado vai para next(e), que cai no tratamento de erros do server.js.

O "pronto → entregue" fica em outra rota, PATCH /:id/recebido, que só aceita exigirTipo("cliente"), confere se o pedido é do cliente e se o status é pronto.

Aprofundar: o que acontece quando o cliente aceita um orçamento src/rotas/orcamentos.js
1

→
2

A partir daí, só esse fabricante consegue ver o pedido (os outros deixam de enxergá-lo), avançar a produção e conversar no chat.

  • src/validar.js: confere dados

🗄️ supabase/ — o banco

  • schema.sql: cria as tabelas
  • migracao-02-google-convites.sql: Google + convites
  • migracao-03-status-pronto.sql: status "pronto"

  • android/: projeto Android (Gradle)
  • versao-apk.js e copiar-apk.js: geram o APK numerado

  • docs/diagramas.md: diagramas Mermaid
  • package.json: bibliotecas e comandos
  • .env.example: modelo das chaves (o .env real não vai pro GitHub)
Pense num restaurante: public/ é o salão (o que o cliente vê), o servidor é a cozinha (onde as regras são aplicadas), o banco é a despensa (onde tudo fica guardado) e o app é um delivery que leva o mesmo cardápio para o celular.

Assunto 5

Arquitetura e a API

Em uma fraseO navegador e o app nunca falam direto com o banco: eles sempre pedem ao servidor, e o servidor confere quem é a pessoa e o que ela pode fazer.

Uma chamada passa por 4 "portões" no servidor antes de mexer no banco.

O servidor é um garçom. O cliente (navegador) não entra na cozinha nem mexe na despensa (banco). Ele faz o pedido ao garçom, que confere a comanda (token), vê se o pedido é permitido, e só então vai à cozinha.

O que é a API?

API é a lista de "pedidos" que o servidor aceita. Cada item é uma rota: um método (o verbo) + um endereço. A resposta vem em JSON, um formato de texto para dados.

GET

Buscar/ler. Ex.: GET /api/pedidos lista os pedidos.

POST

Criar/enviar. Ex.: POST /api/pedidos/7/orcamentos.

PATCH

Mudar uma parte. Ex.: PATCH /api/pedidos/7/status.

DELETE

Apagar. Ex.: DELETE /api/pedidos/7.

Os códigos de resposta (status HTTP)

200Deu certo.
201Criado (pedido, orçamento, mensagem).
400Dado errado (campo vazio, preço negativo).
401Não está logado / token inválido.
403Logado, mas não tem permissão.
404Não encontrado.
409Conflito (ex.: já orçou esse pedido).
500Erro interno. Os testes garantem que o usuário nunca cai aqui por erro dele.
Aprofundar: a função api() que todas as telas usam public/js/api.js
  1. 1async quer dizer que a função espera respostas da internet sem travar a tela.
  2. 2Coloca o token (crachá) no cabeçalho Authorization de toda chamada. É assim que o servidor sabe quem é.
  3. 4–7Se estamos mandando dados comuns, transforma em texto JSON. Se for upload de arquivo (FormData), deixa como está.
  4. 10fetch faz a chamada. SERVIDOR é vazio no site e é o endereço do Render no app (assunto 10).
  5. 11–13Se não houver internet, mostra uma frase clara em português em vez de "Failed to fetch".
  6. 16401 = o token venceu ou é inválido: desloga e volta para o login.
  7. 17Qualquer outro erro: lança a mensagem que o servidor mandou (ex.: "Este pedido não é seu.").
Aprofundar: os "porteiros" exigirLogin e exigirTipo (middleware) src/autenticacao.js

Middleware é uma função que roda antes da rota. Ela pode deixar passar (next()) ou barrar com um erro.

  1. 2–3Pega o cabeçalho Authorization: Bearer xxxxx e tira a palavra "Bearer " para sobrar só o token.
  2. 6jwt.verify confere a assinatura (foi o nosso servidor que criou?) e a validade (7 dias). Token falso ou vencido cai no catch: 401.
  3. 12–13Importante: busca o papel atual no banco. Se o dono tirar o cargo de fabricante de alguém, vale na hora, mesmo que o token antigo diga "fabricante".
  4. 14Se a conta foi apagada: 401.
  5. 15Guarda os dados em req.usuario, para a rota saber quem está chamando.
  6. 16next() = "pode passar".
  7. 20–27exigirTipo("fabricante") é uma função que cria outro porteiro. Ele só deixa passar quem tem aquele tipo; os outros recebem 403.

Uso numa rota: rotas.post("/pedidos/:id/orcamentos", exigirLogin, exigirTipo("fabricante"), async (req, res) => {...}). Lê-se: "primeiro confere login, depois confere se é fabricante, depois faz o trabalho".

Aprofundar: validação dos dados src/validar.js

Antes de gravar qualquer coisa, o servidor confere o que chegou. Nunca confiamos só no formulário da tela, porque alguém pode chamar a API direto, sem usar a tela.

  1. 2Campo vazio = "não preenchido" (null). É permitido, porque medidas são opcionais.
  2. 4Uma expressão regular (regex) confere se só tem dígitos. "abc" ou "1.5" viram NaN ("não é número") = inválido.
  3. 6Também tem que estar dentro do limite (ex.: quantidade de 1 a 10000).
  4. 10–12Data: além do formato AAAA-MM-DD, confere se o dia existe de verdade. "2026-02-31" vira outra data no JavaScript, então não bate com o texto: inválida.

Outras validações: título/descrição obrigatórios e cortados no tamanho máximo, prazo não pode ser no passado, só arquivos .stl .obj .3mf .jpg .jpeg .png .webp .pdf, preço maior que zero, prazo do orçamento de 1 a 3650 dias, id da URL tem que ser número (idValido).

Banco de dados

Em uma fraseSão 6 tabelas no PostgreSQL ligadas por ids, com regras (constraints) que o próprio banco garante, mesmo se o código errar.

As regras que o banco garante sozinho

✅ check

Só aceita valores da lista. Ex.: status só pode ser um dos 6 status; preco > 0; quantidade > 0.

🔑 unique

Não deixa repetir. Ex.: e-mail único; unique (pedido_id, fabricante_id) = cada fabricante manda só 1 orçamento por pedido.

🧹 on delete cascade

Apagou o pedido? Os anexos, orçamentos e mensagens dele somem junto, sem sobrar lixo.

👑 um dono só

Índice único parcial um_dono_so: só uma linha pode ter dono = true.

✉️ convite pendente único

Não pode ter dois convites ainda não usados para o mesmo e-mail.

🔒 RLS ligado

Row Level Security ligado sem regras públicas: ninguém de fora lê as tabelas. Só o servidor, com a chave secreta.

Aprofundar: a tabela de orçamentos em SQL supabase/schema.sql
  1. 2id numérico que o banco gera sozinho (1, 2, 3...). primary key = identifica a linha.
  2. 3references pedidos(id) = chave estrangeira: tem que existir esse pedido. on delete cascade = apagou o pedido, apaga o orçamento.
  3. 5numeric(10,2) = número com 2 casas decimais (dinheiro). O check recusa zero ou negativo.
  4. 8–9Começa como pendente e só pode ser um dos 3 valores.
  5. 11Se o mesmo fabricante tentar orçar duas vezes, o banco devolve o erro 23505, e a rota transforma em 409 "Você já enviou um orçamento para este pedido."

Assunto 7

Login com Google

Em uma fraseO Google confirma quem a pessoa é; o nosso servidor confere essa confirmação e entrega o "crachá" do PrintHub (token JWT), que vale 7 dias.
É como entrar num evento: você mostra o RG (Google) na portaria, e recebe uma pulseira do evento (nosso token). Dali em diante, em cada área você só mostra a pulseira. A pulseira tem um selo que só o organizador sabe fazer (a assinatura com JWT_SECRET), então ninguém falsifica.

Assunto 8

Telas ao vivo (polling)

Em uma fraseA cada 3 segundos a tela pergunta ao servidor "mudou alguma coisa?" e só redesenha o que mudou.
É como uma criança no carro perguntando "já chegou?" a cada 3 segundos. Simples e funciona. A alternativa (SSE/WebSocket) seria o motorista avisar sozinho quando chegar: mais eficiente, mas mais complicado de montar.

Por que polling e não SSE/WebSocket?

Polling

  • Usa a mesma rota que a tela já usava
  • Funciona igual no site e no app
  • Se a internet cair, a próxima pergunta simplesmente tenta de novo
  • Fácil de explicar e de manter
  • Custo: uma chamada a cada 3 s por tela aberta (pequeno com poucos usuários)

SSE / WebSocket

  • O servidor avisa na hora (mais eficiente)
  • Precisa manter uma conexão aberta por pessoa
  • Precisa reconectar quando cai, e o plano grátis do Render derruba conexões ao dormir
  • Mais código e mais coisa para dar errado no prazo

Cuidados para não atrapalhar quem está usando

👀 Só com a tela visível

Se a aba está escondida ou o app minimizado (document.hidden), não pergunta. Quando a pessoa volta, atualiza na hora.

🔍 Só redesenha se mudou

Faz um "resumo" (assinatura) do pedido e compara com o anterior.

⌨️ Não apaga o que a pessoa digita

Se o fabricante está preenchendo o orçamento ou alguém está confirmando uma exclusão, aquela parte não é redesenhada.

✨ Destaque no que é novo

Pedido ou orçamento que acabou de chegar ganha a classe novo, que pisca a cor por 6 s (animação CSS chegou).

💬 Chat só pede o que falta

?depois=ID: o servidor devolve só mensagens com id maior que a última da tela.

🗑️ Pedido excluído

Se o pedido some enquanto a tela está aberta, aparece "Este pedido foi excluído" com link para voltar.

🧮 Versão = hash

Um hash é uma "impressão digital" de um conteúdo. Mudou uma vírgula em qualquer tela, o hash muda. Usamos os 12 primeiros caracteres do SHA-256 como número de versão. Ninguém precisa lembrar de aumentar a versão.

✅ Checksum

Hash SHA-256 do próprio .zip. O app confere se o arquivo chegou inteiro e sem alteração antes de usar.

🔧 Modo manual

No capacitor.config.json: "autoUpdate": false e "appReadyTimeout": 10000. Nós controlamos quando conferir (uma vez por abertura, marcado em sessionStorage).

🔢 Por que o APK tem versão própria

O plugin só percebe que um APK novo foi instalado quando o versionCode muda. Aí ele descarta as telas baixadas antes e usa as que vieram no APK novo. Sem isso, o app continuaria com telas antigas baixadas.

Aprofundar: o servidor montando o pacote src/rotas/app.js
  1. 1–2Cria um .zip vazio e começa um cálculo de hash.
  2. 3–7Para cada arquivo de public/ (sempre na mesma ordem): coloca no zip e "alimenta" o hash com o nome e o conteúdo.
  3. 8A versão é o hash em hexadecimal, cortado em 12 caracteres (ex.: a3f9c0e1b2d4).
  4. 9–10O zip vira bytes na memória, e calculamos o checksum dele.
  5. 12–14A rota responde com a versão, onde baixar e o checksum. Isso tudo é feito uma vez, quando o servidor liga; as telas só mudam com um deploy novo, e aí o servidor liga de novo.
"Para não precisar reinstalar o app a cada mudança, o servidor monta um .zip das telas com uma versão que é o hash do conteúdo. O app confere a versão ao abrir, baixa se mudou, valida com checksum, e se a versão nova falhar ele volta sozinho para a anterior."
Assunto 12

Segurança

Em uma fraseSegurança em camadas: mesmo que uma falhe, a próxima segura.
Como uma casa com portão, porta, chave e cofre. Passar pelo portão não abre o cofre.

🎫 Token JWT

Toda rota protegida exige o token. Falso, vencido ou de outro segredo: 401.

🔄 Papel conferido no banco

A cada chamada, exigirLogin busca o papel atual. Tirou o cargo? Vale na hora.

🚧 Permissões

Só cliente cria pedido, só fabricante orça, só o escolhido avança, só o cliente aceita e confirma recebimento. Pedido de outro cliente: 403/404.

🧾 Validação

O servidor confere tudo que chega, mesmo que a tela já confira. Alguém pode chamar a API sem usar a tela.

🛡️ XSS: função esc

Todo texto digitado por usuários passa por esc() antes de ir para a tela, trocando < por &lt;. Assim, se alguém escrever <script> no título, aparece como texto e não roda.

📎 Arquivos

Só extensões permitidas, até 5 arquivos de 20 MB, nome limpo + código aleatório, bucket privado e links que expiram em 1 hora.

🔐 Chaves em variáveis de ambiente

A chave secreta do Supabase e o JWT_SECRET ficam no .env (local) e no Render. O .env está no .gitignore: nunca vai para o GitHub.

🌍 Repositório público

O código é público, mas isso não é problema: a segurança não depende de esconder o código, e sim das chaves, que não estão nele. A chave "publishable" é feita para ficar no navegador.

🗄️ RLS no banco

Mesmo com a chave pública, ninguém lê as tabelas direto: o RLS está ligado sem regras públicas.

🔑 Senhas

Ninguém cadastra senha: o login é Google. As contas de teste guardam só o hash bcrypt.

🚪 CORS fechado

Só a origem do app é liberada para chamar a API de fora.

🙈 Não revela o que existe

Tentar excluir pedido que não é seu dá 404 "não encontrado", e não "existe mas é de outro".

Aprofundar: a função esc public/js/api.js

  2. 3Troca cada um pelo seu "código de escape". O navegador mostra o símbolo, mas não o entende como HTML.

Exemplo: <b>oi</b> vira &lt;b&gt;oi... e aparece na tela literalmente como "<b>oi</b>", sem negrito.

Por que não usou React, Vue ou outro framework? tecnologia

Pelo prazo e para entender tudo o que está no código. HTML, CSS e JavaScript puro não precisam de compilação nem de biblioteca extra, e são a base que qualquer framework usa por baixo. O projeto tem poucas telas, então um framework não traria muito ganho.

Por que Capacitor e não React Native ou Flutter? app

Capacitor reaproveita as mesmas telas do site. Com React Native ou Flutter eu teria que reescrever todas as telas em outra linguagem. Com o prazo curto, reaproveitar foi a melhor escolha, e qualquer melhoria no site aparece no app também.

Por que o navegador não acessa o banco direto? arquitetura

Porque as regras (quem pode ver, quem pode mudar) ficariam no navegador, e qualquer pessoa pode mexer no navegador. Com o servidor no meio, as regras ficam num lugar que o usuário não controla, e a chave secreta do banco nunca sai de lá.

O que é um JWT e por que usou? segurança

É um token, um texto assinado que diz "este é o usuário X". O servidor cria no login e o navegador manda em toda chamada. Como é assinado com um segredo que só o servidor conhece, ninguém consegue falsificar. Vale por 7 dias.

Se o token diz "fabricante" e o dono remove o cargo, a pessoa continua fabricante por 7 dias? segurança

Não. A cada chamada o exigirLogin busca o papel atual no banco, então a mudança vale na hora. O token só prova quem a pessoa é; o que ela pode fazer vem do banco.

Por que o login do app é diferente do site? login

O Google bloqueia login dentro de WebView (o navegador embutido do app), por segurança. No app usamos a janela nativa do Android, que devolve um idToken. Esse idToken vai para o Supabase e daí em diante o fluxo é igual ao do site.

O que é o nonce no login do app? login

Um número aleatório de uso único. O Google recebe ele resumido e coloca dentro do token; o Supabase recebe o original e confere se bate. Isso impede que alguém reaproveite um token antigo ou roubado.

Por que polling e não WebSocket? ao vivo

Polling é mais simples: usa as mesmas rotas, funciona igual no site e no app e se recupera sozinho se a internet cair. Para poucos usuários o custo de uma chamada a cada 3 segundos é pequeno. Com muitos usuários, eu trocaria por WebSocket ou pelo Realtime do Supabase.

Como você garante que um fabricante não vê pedidos de outro? permissões

Pela regra em permissoes.js: fabricantes só veem pedidos ainda abertos (para orçar). Depois que o cliente aceita um orçamento, só o fabricante escolhido continua vendo. E cada fabricante só vê o próprio orçamento, não o dos concorrentes.

O que acontece se dois fabricantes mandarem orçamento ao mesmo tempo? E se o mesmo mandar dois? banco

Dois fabricantes diferentes: tudo certo, os dois ficam salvos e o cliente compara. O mesmo fabricante duas vezes: o banco recusa por causa do unique (pedido_id, fabricante_id), e a API responde 409 "Você já enviou um orçamento para este pedido".

Onde ficam os arquivos 3D e fotos? São públicos? storage

No Supabase Storage, num bucket privado. O banco guarda só o caminho. Para mostrar, o servidor gera um link temporário que expira em 1 hora, e só para quem tem permissão de ver aquele pedido.

O que é XSS e como você evitou? segurança

É quando alguém escreve código (ex.: <script>) num campo, e esse código roda no navegador de outra pessoa. Evitei com a função esc(), que transforma os caracteres especiais do HTML em texto antes de mostrar qualquer coisa digitada por usuários.

O repositório é público. Isso não é perigoso? segurança

Não, porque nenhuma chave secreta está no código. Elas ficam em variáveis de ambiente (.env no computador, painel do Render na nuvem), e o .env está no .gitignore. Um código seguro não depende de ficar escondido.

Como o app se atualiza sem a Play Store? app

O servidor junta as telas num .zip e calcula uma versão pelo hash do conteúdo. O app pergunta a versão ao abrir; se mudou, baixa, confere o checksum e troca na próxima abertura. Se a versão nova falhar em 10 segundos, ele volta para a anterior. Só mudanças nativas (plugin, permissão, ícone) exigem APK novo.

O que os testes testam? Por que só falhas? testes

Testam o que acontece quando o usuário erra ou tenta algo proibido: 31 casos de token, permissões, dados inválidos e endereços errados. Foquei em falhas porque o caminho feliz eu testo usando o sistema, mas os erros são onde costuma ter brecha de segurança ou "erro interno".

Por que existe o status "pronto" antes de "entregue"? regra

Para quem confirma a entrega ser o cliente, não o fabricante. O fabricante marca "pronto" quando a peça está feita, e o cliente toca em "Recebi o pedido". Assim ninguém diz que entregou sem o cliente confirmar.

Por que o cliente não pode excluir um pedido em produção? regra

Porque um fabricante já está trabalhando nele (e gastando material). O cliente só exclui quando ninguém está trabalhando: aberto, com orçamentos ainda não aceitos, ou já entregue. Nas outras etapas a tela pede para conversar com o fabricante pelo chat. Só o dono da plataforma pode excluir em qualquer etapa, para administrar.

Como alguém vira fabricante? papéis

Só por convite do dono. Na aba Equipe ele cadastra um e-mail; quando essa pessoa entra com o Google usando aquele e-mail, a conta já vira fabricante. Qualquer outra pessoa entra como cliente. Isso evita que qualquer um se diga fabricante.

O que acontece se o servidor cair? deploy

As telas mostram "Sem conexão com o servidor" e tentam de novo sozinhas no próximo ciclo. Os dados não se perdem, porque ficam no Supabase, separado do servidor. No plano grátis do Render, o servidor dorme depois de 15 minutos e acorda em uns 50 segundos.

Isso aguenta muitos usuários? O que você mudaria para crescer? futuro

Para uma escala de projeto acadêmico, sim. Para crescer eu trocaria o polling por tempo real (WebSocket/Supabase Realtime), sairia do plano grátis do Render, colocaria paginação nas listas e usaria transações no aceite de orçamento.

Quais melhorias futuras você faria? futuro

Pagamento dentro da plataforma, avaliação e reputação dos fabricantes, notificações push no celular, visualizador 3D do arquivo .stl, publicação na Play Store e versão para iPhone (o Capacitor também gera iOS).

O que é uma migração no banco? banco

Um arquivo SQL que muda um banco que já tem dados, sem apagar nada. Tive duas: uma para o login com Google e os convites, outra para acrescentar o status "pronto".

Qual foi a maior dificuldade? pessoal

Sugestão (adapte à sua experiência): o login com Google no app, porque o Google bloqueia login em WebView e foi preciso usar o login nativo, configurar um cliente Android com o SHA-1 e entender o nonce. Outra foi a atualização pelo ar, que exigiu versionar o APK.

API
A lista de "pedidos" que o servidor aceita. Cada um é uma rota.
Rota
Método + endereço que o servidor entende. Ex.: GET /api/pedidos.
JSON
Formato de texto para dados: { "nome": "Ana" }.
Token / JWT
"Crachá" assinado que prova quem você é. Vai em toda chamada.
Middleware
Função que roda antes da rota e pode barrar. Ex.: exigirLogin.
Polling
Perguntar de tempos em tempos se algo mudou (aqui, a cada 3 s).
SSE / WebSocket
Conexão aberta em que o servidor avisa sozinho. Alternativa ao polling.
CORS
Regra do navegador: uma página só chama API de outro endereço se o servidor liberar.
Origem (origin)
O "endereço de onde a página veio" (protocolo + domínio + porta).
Deploy
Publicar a nova versão na internet.
Hash
"Impressão digital" de um conteúdo. Mudou um caractere, muda o hash.
SHA-256
O algoritmo de hash usado no projeto.
Checksum
Hash usado para conferir se um arquivo chegou inteiro.
bcrypt
Jeito seguro de guardar senha: guarda o hash, não a senha.
OAuth
Padrão para "entrar com Google/Facebook" sem dar a senha ao site.
PKCE
Versão mais segura do OAuth para navegador: um código que só quem pediu consegue trocar.
idToken
Token que o Google entrega dizendo "esta pessoa é fulano@gmail.com".
Nonce
Número aleatório de uso único que impede reaproveitar token.
WebView
Navegador embutido dentro de um app.
Capacitor
Ferramenta que transforma páginas web num app Android/iOS.
Plugin
Pedaço de código nativo que o JavaScript do app pode chamar (câmera, login).
APK
O arquivo de instalação de um app Android.
Gradle
Ferramenta que compila o projeto Android e gera o APK.
SHA-1 (do app)
Impressão digital da chave que assina o APK. O Google usa para reconhecer o app.
Banco relacional
Banco com tabelas ligadas por ids (PostgreSQL).
Chave primária (PK)
Coluna que identifica cada linha (o id).
Chave estrangeira (FK)
Coluna que aponta para o id de outra tabela.
Constraint / check
Regra que o banco obriga. Ex.: preço > 0.
Cascade
Apagou o "pai", apaga os "filhos" junto.
Migração
Arquivo SQL que muda um banco existente sem perder dados.
RLS
Row Level Security: regra do banco sobre quem lê cada linha.
Bucket
"Pasta" do Storage onde ficam os arquivos.
Link assinado
Link temporário para um arquivo privado (aqui, 1 hora).
Variável de ambiente
Configuração fora do código (chaves, senhas). Fica no .env ou no Render.
.gitignore
Lista de arquivos que o Git não envia (ex.: .env).
Commit
Um "ponto salvo" no histórico do Git.
Branch
Uma linha de trabalho separada. A main é a que vai para o ar.
Push
Enviar commits para o GitHub.
XSS
Ataque em que texto digitado vira código na página de outra pessoa.
Status HTTP
Número da resposta: 200 ok, 400 dado errado, 401 sem login, 403 proibido, 404 não existe.
async / await
Jeito de esperar uma resposta da internet sem travar a tela.
fetch
Função do navegador que faz uma chamada para um endereço.
Regex
Expressão regular: um "molde" para conferir textos. Ex.: /^\d+$/ = só dígitos.
Token de design (CSS)
Variável CSS com uma cor ou tamanho, usada no site inteiro.
Rollback
Voltar para a versão anterior quando a nova falha.
localStorage / sessionStorage
Memória do navegador. O token fica no localStorage; "já conferi atualização" fica no sessionStorage (some ao fechar).
